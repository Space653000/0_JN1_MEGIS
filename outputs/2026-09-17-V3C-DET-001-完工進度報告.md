## 3. 兩層證據定義

### 3.1 L1 `byte_sha256`

對檔案原始 bytes 計算，用於傳輸、Git checkout、儲存與竄改偵測。任何 header 或單一 byte 改變都必須改變 L1。

### 3.2 L2 `semantic_fingerprint`

對 canonical engineering record 計算，用於可重現性與跨平台比較。Canonical JSON 使用 UTF-8、排序 key、無多餘空白，數值依政策捨入後轉為字串：

| 量 | 精度 |
|---|---|
| 長度／座標 | 0.001 mm |
| 面積 | 0.01 mm² |
| 體積 | 0.01 mm³ |
| Rounding mode | `ROUND_HALF_EVEN` |

目前沒有任何 `informationalFields`。若日後證明某拓樸欄位在 ARM64 emulation 與 x64 不穩定，必須有差異證據、ADR 與 policy version 變更，不能直接從 hash 排除。

## 4. Replay 中發現並修正的真實非確定性

第一次 replay 並沒有立即通過，而是依序暴露兩個非語意差異：

1. OpenCascade STEP `PRODUCT` 名稱內含每次 export 遞增的 sequence，例如 `translator 7.9 1`、`translator 7.9 2`。
2. ezdxf 在 OBJECTS section 寫入 `1.4.4 @ <runtime timestamp>` 兩筆 metadata。

處置方式不是放寬 byte 比較，而是只正規化已確認的非工程 metadata。每次正規化後仍用 CadQuery/OCP 重新載入，並要求 STEP B-Rep L2 與 source geometry L2 完全一致，防止正規化誤傷幾何內容。
